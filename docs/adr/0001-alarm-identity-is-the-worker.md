# 报警的身份是工作机，不是弹窗事件

报警服务器需要判断两条先后到达的报警状态说的是不是同一个报警。我们确立：**报警的身份就是工作机 ID，一台工作机同时至多有一个活跃报警**；弹窗事件号降级为"这一次弹窗"的版本号，只用于判断一条迟到的解除消息是否针对当前弹窗。这匹配现实——一台工作机只承载一个抖音中控台会话，不会同时弹出两个验证弹窗。

## 考虑过的方案

**以「工作机 ID + 弹窗事件号」为报警身份**，允许一台工作机存在多个并发报警。被否决的原因不是实现成本，而是语音报不清楚：播报只能念机器标识，连着两遍"3 号机器发现抖音验证弹窗"，听的人无法分辨是两个不同弹窗还是同一个在重复。并发报警要可用，就得先给弹窗一个人能听懂的名字，而目前没有这个概念。

## 后果

- 服务器端活跃报警表以工作机 ID 为键，新的弹窗事件号直接顶替旧的。这是规则的直接表达，不是缓存优化，不要"改成复合键"。
- 解除消息必须比对弹窗事件号后才生效，否则一条迟到的解除会误杀下一次弹窗的报警。
- 解除后一段时间内，同一弹窗事件号的报警状态会被静默丢弃，用于吸收工作机的重发。
- 若将来一台工作机要承载多个直播间会话，本决策需要重开，并且必须同时引入一个可播报的弹窗名称概念。
- 报警去重的可靠性等于工作机 ID 的稳定性。该 ID 与服务器地址存放在同一个配置文件里，文件丢失时会重新生成——即"重装或清配置等于换一台机器"。我们接受这一点，不额外加固：配置丢失时服务器地址也一起丢了，用户不重填就根本连不上、也不会产生报警，所以这个失效模式自带一个更明显的前置故障。心跳超时是最终兜底。
