# 心跳间隔与心跳超时的比例是协议不变量

工作机的心跳间隔（5 秒）和报警服务器的心跳超时（15 秒）是两个写死在不同仓库、不同语言里的常量，3 倍的比例（容许丢两次心跳）是整套机制正确性的前提，却没有在任何一处写出来。我们确立不变量：**心跳间隔 × 3 ≤ 心跳超时**；数字仍在各处写死，改动任一处必须回到本 ADR 重新推导。

## 考虑过的方案

**由报警服务器在应答里下发心跳间隔，工作机遵从。** 时序所有权与[播报文案](./0002-speech-wording-owned-by-server.md)一致，漂移从此不可能。否决原因有两条：一是这要求在"连接已经出问题"的代码路径上增加一层动态配置协商，那是最不该增加活动部件的地方；二是工作机在拿到下发值之前必须有个默认值，那个默认值同样会过期，问题只是换了个位置。若将来要部署多套网络状况差异较大的报警服务器，本决策应当重开。

## 后果

- 违反不变量的表现是**静音**而不是误报：服务器反复判定失联并自动解除，重建的报警因弹窗事件号未变而撞上解除后的抑制窗口，于是报一次之后彻底安静，弹窗一直挂着无人知晓。
- 两侧测试都不会发现违反：工作机测试注入自己的间隔，服务器测试注入自己的时钟，各自都是自洽的。这条不变量目前只由文档和注释守护。
- 工作机的 socket 超时与心跳间隔相等，且上报是串行链，因此一次卡住的连接会吃掉整个心跳周期。3 倍余量能吸收，但吸收后只剩 2 次容差。**不要在不重新推导本不变量的前提下把 socket 超时提到心跳间隔之上。**

## 这两个数字写死在三处

当前代码满足本不变量（5 × 3 = 15），因此无需改动实现。原计划在各常量旁添加互相指向的注释，因程序运行稳定而暂缓——**这三处目前只由本文档关联，代码里没有任何交叉引用**：

- 工作机的心跳间隔常量（`DouyinPopupAlarmService` 构造函数默认值，5 秒）
- 报警服务器的过期判定（`AlarmCoordinator` 的 `Expire`，15 秒）
- 设置页给用户看的说明文字（`PopupAlarmSetting.tsx`，把两个数字都写进了句子里）

第三处容易被漏掉：它不是逻辑，但改了前两个数字而不改它，界面就开始向用户陈述错误的事实。
