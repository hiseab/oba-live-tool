# 语音串行播报带来约 3~4 台的同时报警上限

报警服务器一次只播一句，播完记录该报警的上次播报时间，再按重复间隔公平轮转到下一台。一句播报约 3 秒，默认重复间隔 10 秒，因此同时报警达到 4 台时轮完一圈已超过重复间隔，服务器进入不间断连续播报；6 台以上时语音连成一片，人反而分辨不出是哪几台。**这是语音速率决定的软上限，约 3~4 台同时报警，不是配置项，代码里任何一处都看不到这个数字。** 上限约束的是"同时报警数"，不是接入总数——接入几十台工作机没有问题，只要不会有 5 台同时弹窗。

## 考虑过的方案

**同时报警超过 N 台时改播汇总句**（如"5 台机器发现抖音验证弹窗，请查看服务器列表"）。播报时长恒定，人拿到准确的"有几台"，明细去托盘列表看；实现只需在挑选下一条之前先看活跃数量。暂不实施：4 台以上同时弹窗大概意味着抖音在做批量风控，那种情况下"具体哪几台"已不重要，人反正要逐台去看。

## 后果

- 同时报警较多时，重复间隔实际上失去意义，播报退化为连续流。这不是缺陷，是已接受的行为。
- 缩短重复间隔会更早触发这一退化；延长则单台被提到的频率下降。改动它之前先按"一句约 3 秒 × 同时报警数"重新算一遍。
- 若工作机规模增长到同时 5 台以上弹窗成为常态，应当重开本决策并实施汇总播报。
