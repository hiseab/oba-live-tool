# 播报文案归报警服务器所有

播报文案的措辞规则（含"纯数字读作 N 号机器"）原本在报警服务器和工作机两侧各有一份独立实现，工作机那份只用来在设置页显示预览。两份字字相同，但没有任何机制保证它们继续相同——改了服务器的措辞，工作机的预览就会开始撒谎，且两侧测试都不会失败。我们确立：**措辞只由报警服务器定义**，工作机不再自行渲染，预览改为向服务器索取真实文案。

## 考虑过的方案

**两侧各留一份，加注释互相指向。** 成本最低，且没配服务器时预览也能显示。否决原因：预览的全部价值在于"告诉用户到时候会听到什么"，本地另算的字符串不是预览，只是一段恰好长得像的文本。

**把措辞做成报警服务器的可配置项。** 解决了"改措辞要重新构建两个程序"的问题，但那是新功能，不属于本次去重的范围。本决策不阻挡它——真要做时，措辞的所有者已经是服务器，只需把常量换成配置读取。

## 后果

- `ping` 消息附带机器标识，应答里带回服务器渲染好的示例文案；工作机把它原样显示为预览。协议版本不变——两侧的 JSON 反序列化都会忽略未知字段，加可选字段是兼容的。
- 工作机侧的文案函数及其测试删除。此后工作机代码里不应再出现任何拼装播报文本的逻辑，出现即为回归。
- 预览的前提变成"服务器可达"。地址没填或连不上时，工作机没有预览可显示，只能提示先完成连接测试。这是有意的取舍：拿不到真实文案时，宁可不显示，也不显示一个可能是错的。

## 实施状态：待办

决策已确立，代码尚未改动——当前程序运行稳定，不为此变动。**在实施之前，本文档描述的是目标状态，不是现状。** 现状仍是两侧各有一份实现：服务器的 `SpeechText.Format` 是真正播出去的那份，工作机的 `formatPopupAlarmSpeech` 只喂给设置页预览，两份文案目前字字相同但无任何机制保证同步。设置页那个"服务器**实际**播报内容"标签因此名不副实。

实施时要动的地方：服务器 `WireResponse` 加可选文案字段并在 `ping` 分支渲染；工作机删除 `formatPopupAlarmSpeech` 及其测试断言、设置页改用连接测试返回的文案、修正该标签、处理服务器不可达时无预览可显示的状态。
