# 连接成功后自动启动直播任务

用户每次连接中控台后都要手动开四处开关（自动发言、自动弹窗、评论监听、自动回复），重复且容易漏。我们增加**自动启动**：连接成功后依次开启这些任务。它是一个**按账号配置、默认关闭**的开关，位于直播控制台页面，与无头模式并列。

## 四项界定

**1. "自动回复"指评论监听和自动回复两者，顺序是先监听后回复。** 代码里这是两个独立开关：自动回复的按钮只改渲染层的运行标志，真正拉取消息的是评论监听。只开前者，界面显示运行中但永远静默——那正是[工作机不提示送达失败](./0004-worker-does-not-surface-delivery-failure.md)里那种"看起来在工作、实际没有"的形状，不再制造第二个。

**2. 配置为空的任务照常尝试启动，失败就报错。** 自动发言无话术、自动弹窗无商品时，主进程的既有校验会让任务创建失败并弹出错误提示。已知代价：新建账号的默认配置是空的，**首次连接必然吃到两个错误提示**，尽管用户并没做错什么。选择接受，因为报错同时也在提醒"这个任务还没配"。

**3. 抖音团购（`eos`）平台上禁用该开关，并注明原因。** 八个平台中它是唯一结构上不具备自动回复能力的。第 2 条针对"能做但没配"——配好即可消除；平台不支持属于"做不到"，报错一百次也没有新信息。这不是第 2 条的例外，而是划清它的适用范围。

**4. 开关按账号存储**，与既有的每账号上下文形状一致，多账号互不影响。

## 后果

- 连接成功的时刻不等于"可以开始干活"的时刻：未登录时连接流程会中途打开浏览器等用户手动登录，登录完成后任务**立即**开始发言，此时可能尚未开播或还没准备好。开关默认关闭正是为此——用户需要保留"这次不自动开"的余地。
- 该功能改变了"点连接"的既有含义（原先只是连接）。默认关闭使老用户行为不变。
- **与 [ADR-0005](./0005-detect-popup-via-os-window-title.md) 相互作用，需重新验证**：开启评论监听会新开一个页面并跳转到罗盘大屏。此前该页面只在用户手动开启监听时出现，现在每次连接都会出现，即每次连接都改变标签页布局。而验证弹窗检测依赖 Chromium 的活动标签页标题，ADR-0005 已注明"改变应用开页方式时需重新验证"。**本功能上线前必须确认验证弹窗仍能被检出。**

## 实施状态：已实施

编排逻辑与 React 分离，放在 `src/hooks/useAutoStart.ts`（纯函数，`tests/autoStart.test.ts` 覆盖顺序、失败隔离与平台判定）；开关存于每账号的直播控制台上下文并持久化；接线与开关 UI 在 `StatusCard.tsx`。

上线前仍需人工确认上述 ADR-0005 相互作用：开启自动启动后连接一次，确认验证弹窗仍能被检出。
