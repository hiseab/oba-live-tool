# 弹窗检测基于 OS 窗口标题，不基于页面 DOM

验证弹窗出现在受控 Chromium 里的网页中控台上。我们通过一个常驻 PowerShell 子进程枚举 Windows 可见顶层窗口、匹配标题子串 `人机交互` 来检测它，**不**在页面内用 DOM 查询检测。理由是本仓库既有原则"不依赖易变 DOM class"——抖音的页面结构会随官方升级变化，窗口标题相对稳定，且检测代码完全不必接触中控台页面。

## 考虑过的方案

**在受控页面里用 Playwright 检测弹窗元素。** 最准确，能同时消除下述误检和漏检。否决原因：与"不依赖易变 DOM class"原则直接冲突，且要删掉整个窗口枚举模块、把检测搬进平台层，成本远超收益。

**在标题匹配之外增加进程校验**（比对窗口所属 PID 是否属于应用启动的 Chromium），只消除误检。经评估后决定不做：工作机专机专用，误检在实际使用中不会发生。

## 后果 —— 已接受的两类失准

- **误检**：任何标题含 `人机交互` 的可见顶层窗口都会触发报警，与来源进程无关。例如在工作机上用普通浏览器搜索该词，或用编辑器/文件管理器打开含该词的文档（本仓库的文档现在就含这个词）。
- **漏检**：Chromium 的 OS 窗口标题跟随当前活动标签页。若验证弹窗是页面内遮罩，检测成立的前提是它改变了活动标签的标题——因此**切到其他标签页时弹窗仍在但检测不到**。应用自身也会在同一 context 里开新页面（直播明细、直播复盘、评论监听）。
- 结合[工作机不提示送达失败](./0004-worker-does-not-surface-delivery-failure.md)：漏检与送达失败都不会产生任何提示，两者叠加即为完全无声。
- 当前实现已在真实环境验证可正常报出，说明现有标签页布局下漏检未发生。改变应用开页方式时需重新验证。
